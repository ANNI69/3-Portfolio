# Building a Site-to-Site IPSec VPN Lab in Cisco Packet Tracer

I wanted to understand site-to-site VPNs the way you actually understand something — not by reading a diagram, but by building one, breaking it, and fixing it. So I set up two simulated "sites" in Cisco Packet Tracer, connected them with a plain routed link, and layered an IPSec tunnel on top. It worked in the end, but not on the first, second, or even third try — and honestly, the debugging was where most of the real learning happened.

## The setup

Two sites, each with a PC behind a switch behind a router, connected via a simulated WAN link:

```
[Site A: 192.168.1.0/24] -- RouterA === WAN (203.0.113.0/30) === RouterB -- [Site B: 192.168.2.0/24]
```

The goal: plain routing works first, then IPSec encrypts the LAN-to-LAN traffic across the WAN link without breaking connectivity.

## Problem #1: the router model doesn't support VPN commands at all

I started with 2911 routers — a reasonable default choice, widely used in Cisco labs. First real command, `crypto isakmp policy 10`, and:

```
% Invalid input detected at '^' marker.
```

My first instinct was a typo or wrong mode. It wasn't. After digging through Cisco's community forums, the actual answer was simpler and more annoying: **Packet Tracer's 2911 image doesn't support crypto/IPSec commands at all**, regardless of licensing. This isn't a real Cisco IOS limitation — physical 2911 hardware supports VPN fine — it's specifically a Packet Tracer simulation gap. The forums pointed to two models that actually work in the simulator: the older **1841**, or the modern **ISR4321**.

Lesson: when a "well-documented" command fails identically on every line of a config block, check whether the *platform* supports the feature before assuming you mistyped something.

## Problem #2: swapping router models means re-addressing everything

Moving to the ISR4321 wasn't just a drag-and-drop swap — the interface naming changed too. The 2911 uses `GigabitEthernet0/0` and `0/1`; the ISR4321 uses `GigabitEthernet0/0/0` and `0/0/1` (three segments). Every interface command, every static route reference, had to be redone with the new naming. Not difficult, but a good reminder that "the same config" doesn't always port cleanly across hardware models — a detail that matters more once you're not just following a tutorial.

## Problem #3: SHA-256 isn't recognized

With the right router model in place, I hit a new wall on the hash algorithm:

```
Router(config-isakmp)#hash sha256
^
% Invalid input detected at '^' marker.
```

Modern IOS documentation everywhere uses `sha256` as a standard option. But Packet Tracer's simulated crypto engine, it turns out, only implements the older `sha` keyword (SHA-1) — every working Packet Tracer IPSec example I could find used `hash sha`, none used `sha256`. Swapped it, and the rest of the ISAKMP policy block went through.

## Problem #4: Diffie-Hellman group 14 isn't recognized either

Same story, different line:

```
Router(config-isakmp)# group 14
^
% Invalid input detected at '^' marker.
```

Group 14 (2048-bit) is the real-world modern baseline for DH groups. Packet Tracer's simulator caps out lower — group 5 (1536-bit) was the strongest supported option that actually worked.

By this point there was a clear pattern: **the simulator implements an older, smaller subset of real IOS crypto capabilities**, and the fix each time was the same — drop to the older/simpler algorithm option, note it, and move on. It's a useful distinction to be able to articulate: this is a Packet Tracer *simulation* constraint, not a real production security decision. In an actual deployment, SHA-1 and group 5 would be considered weak — I'd use SHA-256+ and group 14+ on real hardware.

## Problem #5: "a pre-shared key already exists"

Later, re-running a command I'd already successfully entered earlier produced:

```
A pre-shared key for address mask 203.0.113.2 255.255.255.255 already exists!
```

This one wasn't actually an error — it was IOS correctly refusing a duplicate. The key was already configured from an earlier attempt; the fix was simply to *not* re-run it and move on to the next config block, rather than trying to force it through. A good reminder that not every red-looking message means something is broken — sometimes it means a previous step already worked.

## Where it stands

Plain routing between the two sites verified clean (0% packet loss, correct TTL decrement across both router hops) before any crypto config went in — deliberately, so that if the tunnel later failed, I'd know it was an IPSec-specific problem, not a routing problem underneath it. The ISAKMP policy, pre-shared key, transform-set, and crypto map are now in place on both routers, bound to the WAN-facing interface, with the platform-appropriate algorithm choices (`sha`, group 5) instead of the modern defaults that don't exist in this simulator.

*[Note: swap this closing section for your actual final result once you've confirmed `show crypto isakmp sa` shows QM_IDLE and `show crypto ipsec sa` shows non-zero, incrementing encaps/decaps counters — that's the real proof the tunnel is encrypting traffic, not just that ping still works.]*

## What I'd do differently on real hardware

- Use SHA-256 (or SHA-384) instead of SHA-1, and DH group 14+ instead of group 5 — both were simulator ceilings, not real choices
- Use certificate-based authentication instead of a pre-shared key for anything beyond a lab
- On AWS specifically, this whole concept maps to Site-to-Site VPN (Customer Gateway + Virtual Private Gateway) or Transit Gateway for VPC-to-VPC — the IPSec fundamentals are the same, the implementation is managed
