# Site-to-Site VPN Lab — Build Guide

## What you're building
Two simulated "sites" (Site A and Site B), each with a router and a LAN behind it, connected across a simulated "internet" via an IPSec site-to-site VPN tunnel — so traffic between the two LANs is encrypted, while each site can still separately reach the outside internet.

**⚠️ One honest note before you start:** GNS3 itself is free and open-source, but it doesn't ship with Cisco IOS images — those are Cisco's licensed software. You have two realistic paths:
1. **Cisco Packet Tracer** — free if you register for a Cisco Networking Academy account (free to sign up, no cost), comes with simulated Cisco devices built in, no licensing gray area. **This is the simpler, cleaner path for a resume project** and is what I'd actually recommend given your timeline.
2. **GNS3 with Cisco IOS/IOSv images** — requires you to legitimately obtain an IOS image (e.g., via a Cisco account if you or your college has access, or GNS3's own free IOSv images where available). Don't download IOS images from random file-sharing sites — that's a real licensing violation, not just a technicality.

The steps below work conceptually in either tool — I'll note where Packet Tracer's interface differs from GNS3's.

---

## Architecture

```
[Site A LAN: 192.168.1.0/24] -- [Router A] === IPSec Tunnel === [Router B] -- [Site B LAN: 192.168.2.0/24]
                                     |                              |
                                [WAN link, e.g. 203.0.113.1]   [WAN link, e.g. 203.0.113.2]
```

- Router A: LAN interface `192.168.1.1/24`, WAN interface `203.0.113.1/30`
- Router B: LAN interface `192.168.2.1/24`, WAN interface `203.0.113.2/30`
- A PC/host on each LAN to test end-to-end connectivity

---

## Step 1: Build the topology

**Packet Tracer:** Drag two Generic Routers (e.g., 2911), two switches, and two PCs onto the canvas. Connect: PC1 — Switch1 — RouterA (Gig0/0), RouterA (Gig0/1) — RouterB (Gig0/1) [simulating the WAN link], RouterB (Gig0/0) — Switch2 — PC2.

**GNS3:** Same logical topology using two IOS router nodes, two VPCS (virtual PC) nodes, connected via the built-in switch/link tool.

## Step 2: Basic IP addressing and routing

On **Router A**:
```
enable
configure terminal
hostname RouterA
interface GigabitEthernet0/0
 ip address 192.168.1.1 255.255.255.0
 no shutdown
interface GigabitEthernet0/1
 ip address 203.0.113.1 255.255.255.252
 no shutdown
exit
ip route 192.168.2.0 255.255.255.0 203.0.113.2
```

On **Router B**:
```
enable
configure terminal
hostname RouterB
interface GigabitEthernet0/0
 ip address 192.168.2.1 255.255.255.0
 no shutdown
interface GigabitEthernet0/1
 ip address 203.0.113.2 255.255.255.252
 no shutdown
exit
ip route 192.168.1.0 255.255.255.0 203.0.113.1
```

Configure PC1 with IP `192.168.1.10/24`, gateway `192.168.1.1`, and PC2 with `192.168.2.10/24`, gateway `192.168.2.1`.

**Test before adding VPN:** `ping 192.168.2.10` from PC1 should already succeed (plain, unencrypted routing) — confirm this works first. If basic routing is broken, the VPN layer on top of it will fail for reasons that have nothing to do with IPSec, and you'll waste time debugging the wrong thing.

## Step 3: Define "interesting traffic" (what the VPN should encrypt)

On **Router A**:
```
access-list 100 permit ip 192.168.1.0 0.0.0.255 192.168.2.0 0.0.0.255
```

On **Router B**:
```
access-list 100 permit ip 192.168.2.0 0.0.0.255 192.168.1.0 0.0.0.255
```

This ACL tells the router which traffic should go through the encrypted tunnel (LAN-to-LAN traffic) versus regular routing (everything else).

## Step 4: Configure IKE Phase 1 (ISAKMP) — how the routers authenticate each other and negotiate the tunnel

On **Router A**:
```
crypto isakmp policy 10
 encryption aes 256
 hash sha256
 authentication pre-share
 group 14
 lifetime 86400
exit
crypto isakmp key VpnLabSecretKey123 address 203.0.113.2
```

On **Router B** (mirror, pointing back at A):
```
crypto isakmp policy 10
 encryption aes 256
 hash sha256
 authentication pre-share
 group 14
 lifetime 86400
exit
crypto isakmp key VpnLabSecretKey123 address 203.0.113.1
```

**Note:** In a real lab, use a stronger pre-shared key and understand that pre-shared keys are the simplest but weakest authentication method — certificate-based auth is what production site-to-site VPNs generally use. Worth mentioning you know this distinction in an interview.

## Step 5: Configure IKE Phase 2 (IPSec transform set) — how the actual data is encrypted

On both routers:
```
crypto ipsec transform-set VPN-SET esp-aes 256 esp-sha256-hmac
 mode tunnel
exit
```

## Step 6: Create the crypto map and apply it to the WAN interface

On **Router A**:
```
crypto map VPN-MAP 10 ipsec-isakmp
 set peer 203.0.113.2
 set transform-set VPN-SET
 match address 100
exit
interface GigabitEthernet0/1
 crypto map VPN-MAP
exit
```

On **Router B**:
```
crypto map VPN-MAP 10 ipsec-isakmp
 set peer 203.0.113.1
 set transform-set VPN-SET
 match address 100
exit
interface GigabitEthernet0/1
 crypto map VPN-MAP
exit
```

## Step 7: Test the tunnel

From PC1, ping PC2 again (`ping 192.168.2.10`). The first ping or two may drop while the tunnel negotiates — that's normal, not a failure. Then verify the tunnel is actually up (don't just trust that ping working means the encryption is happening):

```
show crypto isakmp sa
```
Should show `QM_IDLE` state — Phase 1 is up.

```
show crypto ipsec sa
```
Look for `#pkts encaps` and `#pkts decaps` counters incrementing — this confirms packets are actually being encrypted/decrypted, not just routed in plaintext.

## Step 8: Verify it's actually encrypted (not just "traffic passes")

This is the step most people skip, and it's the part that proves you understand *why* this matters, not just that you followed steps. If your tool supports packet capture on the WAN link (GNS3 does, via Wireshark integration), capture traffic on the link between the routers while pinging — you should see ESP packets, not visible ICMP payloads. In Packet Tracer, you won't get packet capture, but the `show crypto ipsec sa` counters are your evidence instead.

## Step 9: Document it for GitHub

Even though this lab lives in a simulator (no live "GitHub repo" of running infrastructure like the VPC project), you can still commit:
- A topology diagram (screenshot from GNS3/Packet Tracer, or redrawn)
- All router configs (`show running-config` output from both routers, saved as `.txt`)
- Output of `show crypto isakmp sa` and `show crypto ipsec sa` showing a working tunnel
- A README explaining what each config block does and why

## Step 10: Troubleshooting commands to know cold before the interview

```
show crypto isakmp sa       # Phase 1 status
show crypto ipsec sa        # Phase 2 status, packet counters
show crypto map             # Crypto map bound to which interface
debug crypto isakmp         # Live debug of Phase 1 negotiation (use sparingly, verbose)
debug crypto ipsec          # Live debug of Phase 2 negotiation
```

Common failure points, worth knowing the *why* not just the fix:
- Mismatched ISAKMP policy (encryption/hash/DH group must match exactly on both sides) → Phase 1 never completes
- Mismatched pre-shared key → authentication failure, visible in `debug crypto isakmp`
- ACL mismatch (traffic defined as "interesting" on one side but not mirrored on the other) → tunnel comes up but specific traffic doesn't trigger it
- Crypto map not applied to the correct interface → nothing happens at all

## Interview talking points this project gives you
- "Walk me through what happens when PC1 pings PC2" — be ready to narrate: routing table match → ACL match ("interesting traffic") → ISAKMP Phase 1 negotiation if tunnel not already up → IPSec Phase 2 SA establishment → packet encrypted and encapsulated → sent to peer → decrypted → delivered to PC2's LAN.
- "Why pre-shared key vs certificates?" — pre-shared keys are simpler to set up for a lab/small deployment, but don't scale well and are weaker; production site-to-sites (and definitely anything at AWS's scale) lean toward certificate-based or more robust key management.
- "What would you change for a cloud environment?" — this maps directly to AWS Site-to-Site VPN (Virtual Private Gateway + Customer Gateway) or VPC peering/Transit Gateway for AWS-to-AWS, which is worth mentioning if you're interviewing for a cloud-adjacent role — shows you can connect the on-prem networking concept to the cloud-native equivalent.

That last connection — tying classic IPSec concepts to how AWS implements the same idea — is a strong thing to say out loud in an interview if it comes up naturally. It shows you're not just memorizing Cisco commands in isolation.
